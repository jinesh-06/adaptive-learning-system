# C File Handling, Streams, Binary I/O, Positioning, Buffering, and Robust File Systems

## 1. Introduction

File handling is the mechanism by which a C program communicates with persistent external data such as text files, binary files, configuration files, logs, databases, and serialized records.

The C standard library models input and output through **streams**. A stream is represented by an object of type `FILE`, normally accessed through a `FILE *` pointer. The `<stdio.h>` header provides functions for opening, closing, reading, writing, positioning, buffering, and diagnosing streams.

A file stream provides an abstraction between a C program and an external file or device. The program normally does not manipulate the internal representation of `FILE` directly.

The major areas of C file handling are:

* Opening and closing streams
* Text and binary input/output
* Character and line-based I/O
* Formatted I/O
* Block I/O using `fread()` and `fwrite()`
* File positioning using `fseek()`, `ftell()`, `fgetpos()`, `fsetpos()`, and `rewind()`
* EOF and error detection
* Stream buffering
* File replacement, renaming, and deletion
* Portable serialization
* Safe and reliable file updates

The current international C language standard is **ISO/IEC 9899:2024**, commonly referred to as C23. ISO states that the standard is designed to promote portability among different data-processing systems.

# 4. The FILE Stream

A C stream is represented by an object of type `FILE`.

Example:

```c
FILE *fp;
```

The application normally accesses the stream through the pointer.

A typical file workflow is:

```text
Filename
   ↓
fopen()
   ↓
FILE *
   ↓
Read / Write / Position
   ↓
fclose()
```

Example:

```c
#include <stdio.h>

int main(void)
{
    FILE *fp = fopen("data.txt", "r");

    if (fp == NULL)
    {
        perror("fopen");
        return 1;
    }

    /* File operations */

    fclose(fp);
    return 0;
}
```

If `fopen()` fails, it returns `NULL`. A program should check this result before using the stream.

---

# 5. Standard Streams

C provides three predefined streams:

```c
stdin
stdout
stderr
```

They represent:

* `stdin` – standard input
* `stdout` – standard output
* `stderr` – standard error output

They are expressions of type `FILE *`.

On many Unix-like systems, these correspond to file descriptors 0, 1, and 2 respectively, but those numeric file-descriptor values are an operating-system convention rather than a requirement that should be treated as universal ISO C behavior.

Example:

```c
fprintf(stdout, "Normal output\n");
fprintf(stderr, "Error message\n");
```

---

# 6. Opening Files with fopen()

The general syntax is:

```c
FILE *fopen(const char *filename, const char *mode);
```

Example:

```c
FILE *fp = fopen("data.txt", "r");
```

If the file cannot be opened:

```c
if (fp == NULL)
{
    perror("Unable to open file");
}
```

# 7. File Access Modes

Common modes include:

| Mode              | Meaning                                      |
| ----------------- | -------------------------------------------- |
| `"r"`             | Open existing file for reading               |
| `"w"`             | Open for writing; create or truncate         |
| `"a"`             | Open for appending                           |
| `"r+"`            | Open existing file for reading and writing   |
| `"w+"`            | Create/truncate file for reading and writing |
| `"a+"`            | Open/create file for reading and appending   |
| `"rb"`            | Read binary data                             |
| `"wb"`            | Write binary data                            |
| `"ab"`            | Append binary data                           |
| `"rb+"` / `"r+b"` | Read/write binary file                       |
| `"wb+"` / `"w+b"` | Create/truncate binary file for read/write   |
| `"ab+"` / `"a+b"` | Append binary file with read access          |

For append modes, writes are directed to the end of the file regardless of the current position indicator.

---

# 8. Update Streams

Modes containing `+` allow both input and output.

Examples:

```c
"r+"
"w+"
"a+"
```

There is an important sequencing rule when switching between reading and writing on an update stream.

For example:

```c
fread(...);
fseek(fp, 0, SEEK_CUR);
fwrite(...);
```

or:

```c
fwrite(...);
fflush(fp);
fread(...);
```

The appropriate positioning or flushing operation must be used when switching between input and output according to the stream's mode and previous operation.

# 9. Closing Files

Syntax:

```c
int fclose(FILE *stream);
```

Example:

```c
if (fclose(fp) != 0)
{
    perror("fclose");
}
```

Closing an output stream also performs the necessary stream cleanup and flushing associated with closing it.

Checking the return value can detect errors that occur while final buffered output is being processed.

# 10. Text Streams and Binary Streams

## Text Stream

A text stream represents character-oriented data.

Example:

```text
students.txt
config.txt
log.txt
```

Text streams can involve implementation-defined or system-specific transformations. Therefore, programs should not assume that the physical byte representation of a text stream is identical on every platform.

## Binary Stream

A binary stream is intended for arbitrary bytes.

Example:

```text
students.dat
image.bin
backup.db
```

Binary mode is particularly important when the exact byte representation must be preserved.

Example:

```c
FILE *fp = fopen("data.bin", "rb");
```

and:

```c
FILE *fp = fopen("data.bin", "wb");
```

---

# 11. Character-Oriented I/O

## fgetc()

Reads one character from a stream.

```c
int ch = fgetc(fp);
```

The return type is `int`, not `char`, because `fgetc()` must be able to represent every possible unsigned character value as well as `EOF`.

Correct loop:

```c
int ch;

while ((ch = fgetc(fp)) != EOF)
{
    putchar(ch);
}
```

After the loop:

```c
if (ferror(fp))
{
    perror("Read error");
}
```

---

# 12. fputc()

Writes one character.

```c
fputc('A', fp);
```

Example:

```c
FILE *fp = fopen("output.txt", "w");

if (fp == NULL)
{
    perror("fopen");
    return 1;
}

fputc('H', fp);
fputc('i', fp);

fclose(fp);
```

---

# 13. Line-Oriented I/O

## fgets()

Syntax:

```c
char *fgets(char *buffer, int size, FILE *stream);
```

Example:

```c
char buffer[256];

while (fgets(buffer, sizeof buffer, fp) != NULL)
{
    printf("%s", buffer);
}
```

`fgets()` reads at most `size - 1` characters and terminates the stored string with a null character when successful.

If a newline is read and fits in the buffer, it is retained.

---

# 14. fputs()

Writes a string to a stream.

```c
fputs("Hello World\n", fp);
```

Unlike `puts()`, `fputs()` does not automatically append a newline.

---

# 15. Formatted File I/O

## fprintf()

Writes formatted data to a stream.

```c
fprintf(fp, "%s,%d,%.2f\n", name, id, gpa);
```

Example:

```c
fprintf(fp, "Alice,101,3.92\n");
```

## fscanf()

Reads formatted data from a stream.

```c
fscanf(fp, "%d %lf", &id, &gpa);
```

However, `fscanf()` requires careful format checking because malformed input can cause conversion failures.

For robust applications, a common approach is:

```text
fgets()
   ↓
validate input
   ↓
parse fields
```

instead of relying entirely on `fscanf()`.

# 16. Block I/O

C provides direct block-oriented operations:

```c
fread()
fwrite()
```

## fwrite()

Syntax:

```c
size_t fwrite(
    const void *ptr,
    size_t size,
    size_t count,
    FILE *stream
);
```

Example:

```c
int numbers[5] = {10, 20, 30, 40, 50};

size_t written =
    fwrite(numbers, sizeof numbers[0], 5, fp);

if (written != 5)
{
    perror("fwrite");
}
```

## fread()

Syntax:

```c
size_t fread(
    void *ptr,
    size_t size,
    size_t count,
    FILE *stream
);
```

Example:

```c
int numbers[5];

size_t read =
    fread(numbers, sizeof numbers[0], 5, fp);

printf("Elements read: %zu\n", read);
```

The return value represents the number of objects successfully read or written, not simply the number of bytes.

The official C I/O interface includes both `fread()` and `fwrite()` for direct/block input and output.

# 17. Correct EOF Handling

A common mistake is:

```c
while (!feof(fp))
{
    fread(&record, sizeof record, 1, fp);
    process(record);
}
```

This is incorrect because `feof()` becomes true only after an input operation has encountered end-of-file.

Correct:

```c
while (fread(&record, sizeof record, 1, fp) == 1)
{
    process(record);
}
```

Then distinguish the reason for termination:

```c
if (ferror(fp))
{
    perror("File read error");
}
else if (feof(fp))
{
    printf("End of file reached.\n");
}
```

This pattern is consistent with the standard stream model.

---

# 18. feof()

Syntax:

```c
int feof(FILE *stream);
```

`feof()` tests whether the stream's end-of-file indicator is set.

Important:

```text
feof() does NOT predict EOF.
```

Instead:

```text
read operation
      ↓
attempt reaches EOF
      ↓
EOF indicator becomes set
```

Therefore:

```c
while (!feof(fp))
```

should generally not be used as the primary file-reading condition.

---

# 19. ferror()

Syntax:

```c
int ferror(FILE *stream);
```

It tests whether the stream's error indicator is set.

Example:

```c
if (ferror(fp))
{
    perror("I/O error");
}
```

A non-zero return value indicates that an error has occurred on the stream.

---

# 20. perror()

`perror()` prints a programmer-supplied message followed by a description associated with the current `errno` value.

Example:

```c
FILE *fp = fopen("missing.txt", "r");

if (fp == NULL)
{
    perror("fopen");
}
```

Possible output:

```text
fopen: No such file or directory
```

The exact wording is implementation/operating-system dependent.

---

# 21. clearerr()

`clearerr()` clears the EOF and error indicators associated with a stream.

Example:

```c
clearerr(fp);
```

This is useful when a program intentionally wants to continue using a stream after handling an EOF or error condition.

# 22. File Position Indicator

Every file stream maintains a **file position indicator**.

It identifies the position associated with the next input or output operation.

Important functions include:

```c
fseek()
ftell()
fgetpos()
fsetpos()
rewind()
```

These are part of the C file-positioning interface.

---

# 23. fseek()

Syntax:

```c
int fseek(FILE *stream, long offset, int origin);
```

The main origins are:

```c
SEEK_SET
SEEK_CUR
SEEK_END
```

Examples:

```c
fseek(fp, 0, SEEK_SET);
```

Moves to the beginning.

```c
fseek(fp, 10, SEEK_CUR);
```

Moves relative to the current position.

```c
fseek(fp, 0, SEEK_END);
```

Moves to the end.

For binary streams, offsets are measured in bytes from the specified origin. Text streams have stricter positioning rules; arbitrary byte offsets should not be assumed to work the same way as binary streams.

---

# 24. ftell()

Syntax:

```c
long ftell(FILE *stream);
```

Example:

```c
long position = ftell(fp);

if (position == -1L)
{
    perror("ftell");
}
```

For a binary stream, the returned value represents the file position measured from the beginning in bytes.

For a text stream, the returned value is only guaranteed to be meaningful when used according to the rules of `fseek()`.

---

# 25. rewind()

Syntax:

```c
rewind(fp);
```

It moves the file position indicator back to the beginning of the stream.

Example:

```c
rewind(fp);
```

This is often simpler than:

```c
fseek(fp, 0, SEEK_SET);
```

when the program simply needs to restart reading from the beginning.

---

# 26. fgetpos() and fsetpos()

These functions provide another mechanism for saving and restoring a stream position.

Example:

```c
fpos_t position;

if (fgetpos(fp, &position) == 0)
{
    /* Perform operations */

    fsetpos(fp, &position);
}
```

`fpos_t` is the type intended to represent a stream position and associated positioning state.

---

# 27. Stream Buffering

C streams can use internal buffering to reduce the number of interactions with the underlying I/O device.

The standard library provides:

```c
setbuf()
setvbuf()
fflush()
```

The buffering modes include:

```c
_IOFBF
_IOLBF
_IONBF
```

These represent full buffering, line buffering, and unbuffered operation respectively.

However, applications should not assume that every stream has one particular buffering mode by default. Actual behavior can depend on the implementation and the associated device.

---

# 28. setvbuf()

Syntax:

```c
int setvbuf(
    FILE *stream,
    char *buffer,
    int mode,
    size_t size
);
```

Example:

```c
char buffer[8192];

setvbuf(fp, buffer, _IOFBF, sizeof buffer);
```

`setvbuf()` should be called at the appropriate point in the stream lifecycle, before normal I/O operations on the stream.

---

# 29. fflush()

Syntax:

```c
int fflush(FILE *stream);
```

For an output stream, `fflush()` causes buffered output to be transmitted to the associated output device.

Example:

```c
fprintf(fp, "Important data\n");

if (fflush(fp) == EOF)
{
    perror("fflush");
}
```

Important distinction:

```text
fflush()
    ↓
C library buffer
    ↓
associated output device / OS interface
```

It should **not** be interpreted as a universal guarantee that data has already reached permanent physical storage.

# 30. Binary Structure Serialization

A simple binary record can be written using:

```c
typedef struct
{
    int id;
    char name[32];
    double gpa;
} Student;
```

Writing:

```c
fwrite(&student, sizeof student, 1, fp);
```

Reading:

```c
fread(&student, sizeof student, 1, fp);
```

This is convenient when the file is intended for the same implementation/environment.

However, raw structure serialization is **not automatically portable**.

Potential portability problems include:

* Structure padding
* Alignment
* Integer representation
* Floating-point representation
* Byte order
* Different sizes of C types
* Compiler/ABI differences

For portable file formats, explicitly encode fields into a defined representation rather than simply dumping the in-memory structure.

# 31. Random-Access Record Database

Example:

```c
#include <stdio.h>
#include <stdlib.h>

typedef struct
{
    int id;
    char name[32];
    double gpa;
} Student;

int write_records(const char *filename)
{
    FILE *fp = fopen(filename, "wb");

    if (fp == NULL)
    {
        perror("fopen");
        return -1;
    }

    Student students[] =
    {
        {101, "Alice Smith", 3.92},
        {102, "Bob Jones", 3.45},
        {103, "Charlie Brown", 3.78}
    };

    size_t count = sizeof students / sizeof students[0];

    size_t written =
        fwrite(students, sizeof students[0], count, fp);

    if (fclose(fp) != 0)
        return -1;

    return written == count ? 0 : -1;
}
```

Updating a record:

```c
int update_student_gpa(
    const char *filename,
    int target_id,
    double new_gpa)
{
    FILE *fp = fopen(filename, "rb+");

    if (fp == NULL)
    {
        perror("fopen");
        return -1;
    }

    Student student;

    while (fread(&student, sizeof student, 1, fp) == 1)
    {
        if (student.id == target_id)
        {
            student.gpa = new_gpa;

            if (fseek(fp,
                      -(long)sizeof student,
                      SEEK_CUR) != 0)
            {
                perror("fseek");
                fclose(fp);
                return -1;
            }

            if (fwrite(&student, sizeof student, 1, fp) != 1)
            {
                perror("fwrite");
                fclose(fp);
                return -1;
            }

            if (fclose(fp) != 0)
                return -1;

            return 0;
        }
    }

    if (ferror(fp))
    {
        perror("fread");
    }

    fclose(fp);
    return -1;
}
```

The important technique is:

```text
fread()
   ↓
position advances
   ↓
fseek backward by record size
   ↓
fwrite()
   ↓
record overwritten
```

# 32. File Size Calculation

For a binary stream:

```c
long get_file_size(const char *filename)
{
    FILE *fp = fopen(filename, "rb");

    if (fp == NULL)
        return -1;

    if (fseek(fp, 0, SEEK_END) != 0)
    {
        fclose(fp);
        return -1;
    }

    long size = ftell(fp);

    fclose(fp);

    return size;
}
```

This is suitable for many ordinary files, but applications dealing with very large files should use an appropriate platform/API strategy rather than assuming `long` is sufficient everywhere.

# 33. Chunked File Copy

A robust binary-copy pattern is:

```c
#include <stdio.h>

int copy_file(
    const char *source,
    const char *destination)
{
    FILE *src = fopen(source, "rb");

    if (src == NULL)
    {
        perror("Source");
        return -1;
    }

    FILE *dst = fopen(destination, "wb");

    if (dst == NULL)
    {
        perror("Destination");
        fclose(src);
        return -1;
    }

    unsigned char buffer[8192];

    size_t bytes_read;

    while ((bytes_read =
            fread(buffer, 1, sizeof buffer, src)) > 0)
    {
        size_t bytes_written =
            fwrite(buffer, 1, bytes_read, dst);

        if (bytes_written != bytes_read)
        {
            perror("Write");
            fclose(src);
            fclose(dst);
            return -1;
        }
    }

    if (ferror(src))
    {
        perror("Read");
        fclose(src);
        fclose(dst);
        return -1;
    }

    if (fclose(src) != 0)
    {
        perror("Source close");
        fclose(dst);
        return -1;
    }

    if (fclose(dst) != 0)
    {
        perror("Destination close");
        return -1;
    }

    return 0;
}
```

The loop:

```c
while ((bytes_read =
        fread(buffer, 1, sizeof buffer, src)) > 0)
```

is preferable to testing `feof()` before attempting the read.

# 34. Correct Line-Counting Example

A corrected version of the original example is:

```c
#include <stdio.h>

int main(void)
{
    const char *filename = "sample.txt";

    FILE *out = fopen(filename, "w");

    if (out == NULL)
    {
        perror("fopen");
        return 1;
    }

    fprintf(out,
            "Line 1: Cognitive Load Engine\n"
            "Line 2: Adaptive Learning\n"
            "Line 3: Systems C\n");

    if (fclose(out) != 0)
    {
        perror("fclose");
        return 1;
    }

    FILE *in = fopen(filename, "r");

    if (in == NULL)
    {
        perror("fopen");
        return 1;
    }

    char line[256];
    unsigned long line_count = 0;
    size_t total_chars = 0;

    while (fgets(line, sizeof line, in) != NULL)
    {
        line_count++;
        total_chars += sizeof line - 1;

        /* Count actual characters stored in the line */
        size_t length = 0;

        while (line[length] != '\0')
            length++;

        total_chars -= sizeof line - 1;
        total_chars += length;

        printf("[%lu] %s", line_count, line);
    }

    if (ferror(in))
    {
        perror("fgets");
        fclose(in);
        return 1;
    }

    fclose(in);

    printf("\nSummary:\n");
    printf("Lines: %lu\n", line_count);
    printf("Characters read: %zu\n", total_chars);

    return 0;
}
```

A simpler implementation can use `strlen()`:

```c
#include <string.h>

total_chars += strlen(line);
```

# 35. Common Mistakes

## Mistake 1: Not checking fopen()

Incorrect:

```c
FILE *fp = fopen("data.txt", "r");
fgets(buffer, sizeof buffer, fp);
```

Correct:

```c
FILE *fp = fopen("data.txt", "r");

if (fp == NULL)
{
    perror("fopen");
    return 1;
}
```

---

## Mistake 2: Using while (!feof())

Incorrect:

```c
while (!feof(fp))
{
    fread(&record, sizeof record, 1, fp);
    process(record);
}
```

Correct:

```c
while (fread(&record, sizeof record, 1, fp) == 1)
{
    process(record);
}
```

---

## Mistake 3: Ignoring fwrite() result

Incorrect:

```c
fwrite(buffer, 1, size, fp);
```

Better:

```c
if (fwrite(buffer, 1, size, fp) != size)
{
    perror("fwrite");
}
```

---

## Mistake 4: Assuming sizeof(struct) is portable

Incorrect assumption:

```c
fwrite(&student, sizeof student, 1, fp);
```

and then assuming another machine will always interpret the file identically.

Raw structure serialization may contain implementation-dependent representation details.

---

## Mistake 5: Treating fflush() as a disk-sync guarantee

Incorrect:

```text
fflush() = guaranteed permanent disk storage
```

More accurate:

```text
fflush()
= flush C stream output buffering
```

A separate OS/platform mechanism may be required when an application needs stronger durability guarantees.

# 36. Error Handling Pattern

A useful general pattern is:

```c
FILE *fp = fopen("data.bin", "rb");

if (fp == NULL)
{
    perror("fopen");
    return 1;
}

while (fread(buffer, 1, sizeof buffer, fp) > 0)
{
    /* process data */
}

if (ferror(fp))
{
    perror("fread");
}

if (fclose(fp) != 0)
{
    perror("fclose");
}
```

This separates:

```text
Successful input
       ↓
EOF
       ↓
I/O error
```

instead of treating all failed reads as the same condition.

# 37. Performance Considerations

Reading one byte at a time can involve more library-level operations than reading a block.

Instead of:

```c
while ((ch = fgetc(fp)) != EOF)
{
    ...
}
```

for large binary data, a block approach can be appropriate:

```c
while ((n = fread(buffer, 1, sizeof buffer, fp)) > 0)
{
    ...
}
```

Possible buffer sizes include:

```text
4 KB
8 KB
16 KB
64 KB
```

The appropriate size depends on the workload, library, operating system, storage device, and application requirements.

Do not assume that a particular buffer size is universally optimal.

# 38. Security Considerations

## Path Traversal

Avoid constructing paths directly from untrusted user input.

Dangerous example:

```text
../../etc/passwd
```

Applications should validate and constrain paths according to their security requirements.

## File Permissions

Sensitive files should be created with appropriate permissions.

On POSIX systems, mechanisms such as `umask()` influence permissions of newly created files.

## Temporary Files

For sensitive temporary data, use secure platform-supported temporary-file mechanisms rather than constructing predictable temporary filenames manually.

## Data Validation

Never assume that a file contains valid records merely because it has the expected extension.

Validate:

* File size
* Record count
* Field ranges
* Format/version
* Checksums where appropriate
* Input lengths

# 39. Reliable File Replacement

When updating an important file, directly overwriting the original can leave incomplete data if the process terminates during the write.

A common high-level strategy is:

```text
Create temporary file
        ↓
Write complete new contents
        ↓
Flush/close as required
        ↓
Atomically replace original using platform-supported mechanism
```

The exact durability and atomicity guarantees depend on the operating system and filesystem.

---

# 40. Portable Serialization

For portable data exchange, avoid relying exclusively on:

```c
fwrite(&struct, sizeof struct, 1, fp);
```

Instead, define a file format.

For example:

```text
Magic number
Version
Record count
Record 1
Record 2
...
Checksum
```

Each field can have a specified encoding.

Example conceptual format:

```text
ID       → fixed-width integer encoding
Name     → length + UTF-8 bytes
GPA      → explicitly defined numeric representation
```

This approach allows different implementations and programming languages to understand the same file.

# 45. Edge Cases

## Empty File

For an empty file:

```c
fread(...)
```

may immediately return zero objects.

`fgets()` returns `NULL` when no line can be read.

## Partial Read

A read may return fewer objects than requested.

Always check the returned count.

## Partial Write

A write may write fewer objects than requested.

Always verify the return value of `fwrite()`.

## Disk Full

Output operations may fail or write fewer items than requested.

Applications should detect and handle the error.

## Large Files

Do not assume that `long` is large enough for every file on every platform.

Use appropriate platform-specific large-file facilities when required.

# 46. Advanced Architecture

A simplified model is:

```text
Application
     │
     ▼
C Standard I/O
     │
   FILE *
     │
     ▼
Stream Buffer
     │
     ▼
Operating-System I/O
     │
     ▼
Filesystem
     │
     ▼
Storage Device
```

The C standard defines the stream abstraction but does not prescribe a single operating-system implementation underneath it. ISO C is designed to support portable programs across different data-processing systems.

On POSIX/Linux systems, the implementation commonly connects C streams with OS-level file descriptors, but this should be understood as a platform implementation detail rather than a requirement of ISO C.

# 48. Interview Questions

## Beginner

### Q1. What does fopen() return if a file cannot be opened?

`fopen()` returns `NULL`.

The program should check the return value before using the stream.

### Q2. What is FILE *?

It is a pointer to a `FILE` object representing a C I/O stream.

### Q3. What is the difference between "r" and "w"?

`"r"` opens an existing file for reading.

`"w"` opens a file for writing and creates it if necessary or truncates an existing file.

---

## Intermediate

### Q4. Why is while (!feof(fp)) bad practice?

Because the EOF indicator is set only after an input operation encounters end-of-file.

The read function's return value should control the loop.

### Q5. What is the difference between fread() and fgets()?

`fread()` performs block-oriented input.

`fgets()` reads a character string/line from a stream.

### Q6. What is fseek() used for?

It changes the stream's file position indicator.

---

## Advanced

### Q7. Is fwrite(&structure, sizeof structure, 1, fp) portable?

Not necessarily.

The binary representation can depend on structure padding, alignment, byte order, type representations, and implementation details.

### Q8. Does fflush() guarantee that data is physically stored on disk?

No.

`fflush()` handles the C stream's buffered output. Stronger storage-durability guarantees require appropriate platform/filesystem mechanisms.

### Q9. What is the difference between EOF and an I/O error?

EOF indicates that the input operation reached the end of the stream.

An I/O error indicates that an error occurred while performing the operation.

Use:

```c
feof(fp)
```

and:

```c
ferror(fp)
```

to distinguish them.

# 50. Best Practices

1. Always check `fopen()`.
2. Always check important I/O return values.
3. Use `fread()`/`fwrite()` return values to control block-I/O loops.
4. Do not use `while (!feof(fp))` as the main reading condition.
5. Use binary modes for binary data.
6. Use `perror()` when diagnosing failures associated with `errno`.
7. Check `ferror()` after an unsuccessful read when necessary.
8. Check `fclose()` for important output operations.
9. Do not assume `sizeof(struct)` is a portable file format.
10. Define an explicit serialization format when interoperability matters.
11. Do not assume `fflush()` means physical disk durability.
12. Validate untrusted filenames and file contents.
13. Use appropriate permissions for sensitive files.
14. Use temporary-file replacement strategies for critical data.
15. Consider large-file requirements when handling very large files.

# 51. Summary

C file handling is based on the **stream abstraction** provided by `<stdio.h>`.

The most important functions are:

```c
fopen()
fclose()

fgetc()
fputc()
fgets()
fputs()

fprintf()
fscanf()

fread()
fwrite()

fseek()
ftell()
fgetpos()
fsetpos()
rewind()

feof()
ferror()
clearerr()
perror()

setbuf()
setvbuf()
fflush()
```

The fundamental rule for reliable file reading is:

```text
Check the return value of the read operation.
```

For example:

```c
while (fread(buffer, 1, sizeof buffer, fp) > 0)
{
    /* process data */
}
```

rather than:

```c
while (!feof(fp))
{
    /* incorrect primary loop condition */
}
```

For binary files:

```c
fopen("data.bin", "rb");
fopen("data.bin", "wb");
```

For random access:

```c
fseek()
ftell()
```

For error diagnosis:

```c
ferror()
perror()
```

For output buffering:

```c
fflush()
```

The goal of robust C file handling is not merely to read and write files, but to correctly handle **positioning, buffering, partial operations, EOF, errors, portability, security, and data integrity**.

# 52. Key Takeaways

* `FILE *` represents a C I/O stream.
* `fopen()` must be checked for `NULL`.
* `fclose()` should be checked when output reliability matters.
* `stdin`, `stdout`, and `stderr` are predefined standard streams.
* Use `"rb"` and `"wb"` when working with binary data.
* Use `fread()` and `fwrite()` for block I/O.
* Use `fgets()` for safe line-oriented input.
* `feof()` does not predict EOF.
* Use the read function's return value to control reading loops.
* `ferror()` detects stream errors.
* `perror()` provides an `errno`-based diagnostic.
* `fseek()` changes the stream position.
* `ftell()` reports the stream position.
* Text streams and binary streams have different positioning/representation rules.
* `fflush()` flushes C stream output buffering but is not a universal disk-durability guarantee.
* Raw structure serialization is convenient but not inherently portable.
* Explicit serialization formats are preferable for cross-platform data exchange.
* Always validate external file paths and file contents.
* Reliable file handling requires checking return values and handling failure paths.
