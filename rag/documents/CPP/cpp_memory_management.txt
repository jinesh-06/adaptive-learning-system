1. INTRODUCTION
   ============================================================

Memory management is a fundamental part of C++ programming.

C++ provides direct control over object lifetime, storage duration, allocation, and deallocation. This flexibility allows developers to build systems with predictable resource usage and high performance, but incorrect lifetime management can cause:

* Memory leaks
* Dangling pointers
* Use-after-free
* Double deletion
* Invalid memory access
* Buffer overflows
* Double ownership
* Resource leaks
* Exception-safety failures

Modern C++ strongly encourages Resource Acquisition Is Initialization (RAII).

RAII connects the lifetime of a resource to the lifetime of an object.

Examples of resources include:

* Dynamically allocated memory
* Files
* Sockets
* Mutex locks
* Database connections
* Operating-system handles

The Standard Library provides smart pointers:

* std::unique_ptr
* std::shared_ptr
* std::weak_ptr

These types provide standardized ownership models.

IMPORTANT:

Smart pointers do not make every C++ program automatically memory-safe. Incorrect ownership design, raw-pointer misuse, data races, buffer overflows, invalid casts, and lifetime errors can still occur.

The goal of modern C++ memory management is to make ownership explicit and resource lifetime automatic wherever practical.

5. STORAGE DURATION
===================

C++ objects can have different storage durations.

5.1 AUTOMATIC STORAGE DURATION

Local variables that are not declared static or thread_local commonly have automatic storage duration.

Example:

void function() {
int value = 100;
}

The lifetime of value ends when its block is exited.

RAII works particularly well with automatic objects.

---

5.2 STATIC STORAGE DURATION

Objects with static storage duration exist for the duration of the program.

Example:

static int counter = 0;

Namespace-scope objects can also have static storage duration.

---

5.3 THREAD STORAGE DURATION

thread_local objects have thread storage duration.

Example:

thread_local int value = 0;

Each thread has its own instance.

---

5.4 DYNAMIC STORAGE DURATION

Objects can be created using dynamic allocation.

Example:

int* p = new int(42);

The object remains alive until its storage is released appropriately.

Modern C++ normally prefers RAII wrappers instead of manually managing such ownership.

============================================================
6. RAII
=======

RAII means:

Resource Acquisition Is Initialization.

The general idea is:

1. Acquire a resource in an object's constructor or initialization.
2. Use the resource through the object's lifetime.
3. Release the resource in the object's destructor.

Example:

class FileGuard {
private:
FILE* file;

public:
explicit FileGuard(FILE* f)
: file(f) {}

```
~FileGuard() {
    if (file) {
        std::fclose(file);
    }
}
```

};

RAII also works automatically during exception handling.

If an exception leaves a scope, destructors for already-created automatic objects are invoked.

This makes RAII one of the primary techniques for exception-safe resource management.

7. RAW POINTERS VS SMART POINTERS
=================================

A raw pointer such as:

int* p;

is primarily a pointer value.

A raw pointer does not automatically communicate ownership.

It can be used for:

* Non-owning observation
* Pointer arithmetic
* Interoperability with C APIs
* Access to an object whose lifetime is managed elsewhere

A smart pointer combines pointer-like access with ownership semantics.

Main ownership types:

std::unique_ptr
Exclusive ownership.

std::shared_ptr
Shared ownership.

std::weak_ptr
Non-owning observation of an object managed by shared ownership.

============================================================
8. STD::UNIQUE_PTR
==================

std::unique_ptr represents exclusive ownership.

Example:

std::unique_ptr<int> p = std::make_unique<int>(42);

Only one unique_ptr owns the object at a time.

unique_ptr cannot be copied:

std::unique_ptr<int> p1 = std::make_unique<int>(10);

// std::unique_ptr<int> p2 = p1;   // ERROR

Ownership can be transferred using move semantics:

std::unique_ptr<int> p2 = std::move(p1);

After the move, p1 is empty.

Typical state:

Before move:

p1 ---> object
p2 ---> nothing

After move:

p1 ---> nullptr
p2 ---> object

============================================================
9. STD::MAKE_UNIQUE
===================

std::make_unique was introduced in C++14.

Example:

auto ptr = std::make_unique[std::string](std::string)("Hello");

Advantages:

* Clear ownership
* Exception-safe construction
* Avoids explicit new in normal code
* Works naturally with move semantics

Example:

auto number = std::make_unique<int>(100);

std::cout << *number << '\n';

============================================================
10. UNIQUE_PTR ARRAYS
=====================

unique_ptr supports arrays.

Example:

std::unique_ptr<int[]> values =
std::make_unique<int[]>(5);

for (int i = 0; i < 5; ++i) {
values[i] = i * 10;
}

The correct array form automatically uses the appropriate deletion mechanism.

However, for most application code, std::vector is usually preferable when a dynamically sized collection is required.

============================================================
11. CUSTOM DELETERS WITH UNIQUE_PTR
===================================

A unique_ptr can use a custom deleter.

This is useful for resources that do not use delete.

Example:

#include <cstdio>
#include <memory>

int main() {
FILE* raw = std::fopen("data.txt", "r");

```
if (!raw) {
    return 1;
}

std::unique_ptr<FILE, decltype(&std::fclose)>
    file(raw, &std::fclose);
```

}

When file goes out of scope, fclose is called.

The deleter type is part of the unique_ptr type:

std::unique_ptr<T, Deleter>

Therefore, different deleter types produce different unique_ptr types.

============================================================
12. STD::SHARED_PTR
===================

std::shared_ptr represents shared ownership.

Example:

auto p1 = std::make_shared<int>(100);

auto p2 = p1;

Both p1 and p2 share ownership of the same object.

Conceptually:

p1 ----

---> object
/
p2 ----/

The object is destroyed when the last shared owner releases ownership.

use_count() can report the number of shared owners:

std::cout << p1.use_count() << '\n';

However, use_count() should generally not be used as application-level synchronization logic because ownership can change concurrently and the value is only a snapshot.

============================================================
13. SHARED_PTR CONTROL BLOCK
============================

A shared_ptr commonly uses a separate control block.

The control block may contain information such as:

* Number of shared owners
* Number of weak references
* Deleter
* Allocator information
* Other implementation-specific bookkeeping

Conceptually:

shared_ptr
+------------------+
| managed pointer  |
+------------------+
| control pointer  |
+------------------+

Control block:

+----------------------+
| strong ownership     |
| weak ownership       |
| deleter              |
| allocator information|
| implementation data  |
+----------------------+

The exact layout and size are implementation-dependent.

The C++ standard does NOT require a particular number of bytes for a shared_ptr or its control block.

============================================================
14. MAKE_SHARED
===============

Example:

auto ptr = std::make_shared<int>(42);

The implementation commonly performs a combined allocation for the managed object and control-block data.

This can reduce allocation overhead compared with:

std::shared_ptr<int>(new int(42));

However, the standard specifies the semantics rather than requiring a specific physical allocation strategy.

std::make_shared is normally preferred for ordinary shared ownership.

One consideration is that when weak_ptr instances remain, the control block may remain alive after the managed object itself has been destroyed.

============================================================
15. STD::WEAK_PTR
=================

std::weak_ptr represents a non-owning reference to an object managed by std::shared_ptr.

Example:

auto shared = std::make_shared<int>(100);

std::weak_ptr<int> weak = shared;

The weak pointer does not keep the object alive.

To access the object safely:

if (auto locked = weak.lock()) {
std::cout << *locked << '\n';
}

If the object has already been destroyed:

if (auto locked = weak.lock()) {
// Object exists
} else {
// Object no longer exists
}

============================================================
16. CIRCULAR REFERENCES
=======================

A circular shared ownership relationship can prevent destruction.

Example:

class Node {
public:
std::shared_ptr<Node> next;
std::shared_ptr<Node> previous;
};

If:

A -> B

and:

B -> A

both objects may retain shared ownership of each other.

Their reference counts may never reach zero.

Use weak_ptr for a non-owning relationship.

Example:

class Node {
public:
std::shared_ptr<Node> next;
std::weak_ptr<Node> previous;
};

19. STD::ENABLE_SHARED_FROM_THIS
================================

std::enable_shared_from_this allows an object that is already managed by shared_ptr to obtain another shared_ptr that shares the same ownership control block.

Example:

#include <iostream>
#include <memory>

class Widget
: public std::enable_shared_from_this<Widget> {

public:
std::shared_ptr<Widget> get_shared() {
return shared_from_this();
}
};

int main() {
auto widget = std::make_shared<Widget>();

```
auto another = widget->get_shared();

std::cout << widget.use_count() << '\n';
```

}

Both shared pointers share ownership of the same object.

IMPORTANT:

Do NOT do this:

std::shared_ptr<Widget>(this);

inside an object already managed by another shared_ptr.

That can create a separate control block and can result in multiple independent owners attempting to destroy the same object.

shared_from_this() is the standard facility for this use case.

weak_from_this() is also available since C++17.

If shared_from_this() is called when the object is not currently associated with a shared_ptr control block, it can throw std::bad_weak_ptr.

============================================================
20. ALIASING SHARED_PTR
=======================

shared_ptr also supports an aliasing constructor.

This allows a shared_ptr to own one object while storing a pointer to another object or subobject associated with that ownership.

Conceptually:

shared_ptr<Owner> owner;

shared_ptr<Member> member(owner, &owner->member);

The member pointer can remain valid while owner keeps the owning object alive.

This is useful when exposing subobjects while retaining ownership of the containing object.

============================================================
21. CUSTOM DELETERS FOR NON-MEMORY RESOURCES
============================================

Smart pointers can manage resources other than memory.

Examples:

* FILE*
* POSIX file descriptors
* Network sockets
* Operating-system handles
* Library-specific resources

Example:

struct FileCloser {
void operator()(FILE* file) const {
if (file) {
std::fclose(file);
}
}
};

std::unique_ptr<FILE, FileCloser> file(
std::fopen("data.txt", "r")
);

The smart pointer now owns the FILE resource and invokes FileCloser during destruction.

This demonstrates the broader RAII principle:

Resource acquisition
|
v
RAII object
|
v
automatic release

============================================================
22. MOVE SEMANTICS AND OWNERSHIP
================================

unique_ptr is move-only.

Example:

auto p1 = std::make_unique<int>(100);

auto p2 = std::move(p1);

After the move:

* p2 owns the object.
* p1 is empty.

A moved-from unique_ptr is valid but normally contains nullptr.

Ownership transfer is explicit:

std::unique_ptr<Resource> transfer(
std::unique_ptr<Resource> resource
) {
return resource;
}

The caller can transfer ownership using std::move.

============================================================
23. RAW POINTERS AS NON-OWNING POINTERS
=======================================

Raw pointers are not inherently bad.

They are useful when ownership belongs elsewhere.

Example:

void print_value(const int* ptr) {
if (ptr) {
std::cout << *ptr << '\n';
}
}

The function does not delete ptr.

The caller owns the object.

This is different from:

int* ptr = new int(42);

where ptr may represent ownership.

Modern design should make ownership clear through types and interfaces.

============================================================
24. MANUAL NEW AND DELETE
=========================

Traditional dynamic allocation:

int* p = new int(42);

delete p;

For arrays:

int* values = new int[10];

delete[] values;

The allocation and deallocation forms must match.

However, application-level code should normally prefer:

auto p = std::make_unique<int>(42);

or:

auto p = std::make_shared<int>(42);

Manual new/delete may still be required for:

* Custom allocation systems
* Low-level libraries
* Placement construction
* Interoperability
* Specialized ownership designs

============================================================
25. EXCEPTION SAFETY
====================

Manual ownership can leak when exceptions interrupt normal control flow.

Problem:

void bad_function() {
Widget* widget = new Widget();

```
if (some_condition()) {
    throw std::runtime_error("Failure");
}

delete widget;
```

}

If an exception occurs before delete, the object is leaked.

RAII solution:

void good_function() {
auto widget =
std::make_unique<Widget>();

```
if (some_condition()) {
    throw std::runtime_error("Failure");
}
```

}

During stack unwinding, widget's destructor releases the resource.

This is one of the major advantages of RAII.

============================================================
26. PLACEMENT NEW
=================

Placement new constructs an object in storage supplied by the programmer.

Syntax:

new (address) Type(arguments);

Example:

#include <new>

alignas(int) unsigned char buffer[sizeof(int)];

int* p = new (buffer) int(42);

The placement-new expression constructs an int in buffer.

IMPORTANT:

Placement new does NOT allocate the storage.

The storage already exists.

The object lifetime begins when the object is constructed successfully.

For a non-trivial object, its destructor must be invoked appropriately before the underlying storage is reused or released.

Example:

p->~int();

However, explicit pseudo-destructor syntax for scalar types is generally unnecessary in ordinary code. For class types:

object_ptr->~Object();

may be required when manually managing object lifetime.

============================================================
27. FIXED MEMORY ARENA EXAMPLE
==============================

Problem:
Construct objects inside pre-allocated storage.

Code:

#include <cstddef>
#include <iostream>
#include <new>

class Particle {
public:
float x;
float y;
float z;

```
Particle(float px, float py, float pz)
    : x(px), y(py), z(pz) {
    std::cout << "Particle constructed\n";
}

~Particle() {
    std::cout << "Particle destroyed\n";
}
```

};

int main() {
alignas(Particle)
std::byte storage[sizeof(Particle) * 3];

```
Particle* p1 =
    ::new (static_cast<void*>(storage))
    Particle(1.0f, 2.0f, 3.0f);

Particle* p2 =
    ::new (static_cast<void*>(storage + sizeof(Particle)))
    Particle(4.0f, 5.0f, 6.0f);

std::cout << p1->x << '\n';
std::cout << p2->x << '\n';

p2->~Particle();
p1->~Particle();
```

}

The storage remains available after the destructors run.

No delete should be applied to p1 or p2 because they were not obtained from ordinary allocating new.

============================================================
28. ALIGNMENT
=============

Every object type has an alignment requirement.

Example:

alignof(int)

returns the required alignment of int for the implementation.

For custom storage:

alignas(MyType)
std::byte storage[sizeof(MyType)];

can ensure that the storage is suitably aligned for MyType.

Incorrect alignment can result in undefined behavior when an object is accessed through an improperly aligned pointer.

Useful facilities include:

* alignof
* alignas
* std::align
* std::assume_aligned
* std::aligned_alloc

The exact behavior and availability of low-level facilities depend on the language version and platform requirements.

============================================================
29. STD::ALLOCATOR
==================

Allocators separate allocation strategy from container/object management.

The Standard Library provides allocator-related facilities in <memory>.

Example:

std::allocator<int> allocator;

Modern standard containers normally manage allocators internally, so application programmers rarely need to manually use std::allocator for ordinary containers.

Allocator-aware design becomes important when implementing:

* Custom containers
* Memory pools
* Specialized allocation systems
* High-performance systems
* Embedded systems
* Memory-resource based architectures

============================================================
30. POLYMORPHIC MEMORY RESOURCES
================================

C++17 introduced the polymorphic memory resource facilities in <memory_resource>.

Important types include:

* std::pmr::memory_resource
* std::pmr::polymorphic_allocator
* std::pmr::vector
* std::pmr::string
* std::pmr::monotonic_buffer_resource
* std::pmr::unsynchronized_pool_resource
* std::pmr::synchronized_pool_resource

Example:

#include <memory_resource>
#include <vector>

std::byte buffer[1024];

std::pmr::monotonic_buffer_resource resource(
buffer,
sizeof(buffer)
);

std::pmr::vector<int> values(&resource);

values.push_back(10);
values.push_back(20);
values.push_back(30);

The vector obtains memory from the specified memory resource.

This can be useful when allocation strategy needs to be controlled separately from container logic.

============================================================
31. MONOTONIC BUFFER RESOURCE
=============================

std::pmr::monotonic_buffer_resource is useful when many allocations have similar lifetime characteristics.

Memory is obtained from an upstream resource when required.

Individual deallocations are generally not performed as objects are removed.

Instead, memory is reclaimed when the resource itself is released or reset according to its interface.

This makes it useful for:

* Temporary allocations
* Parsing
* Request-scoped memory
* AST construction
* Short-lived workloads

It should not be used when frequent individual deallocation is required.

============================================================
32. POOL MEMORY RESOURCES
=========================

C++17 provides:

std::pmr::unsynchronized_pool_resource

and:

std::pmr::synchronized_pool_resource

Pool resources can efficiently manage repeated allocations of similarly sized blocks.

unsynchronized_pool_resource is intended for cases where external synchronization is unnecessary.

synchronized_pool_resource provides synchronization suitable for concurrent access patterns supported by its interface.

The choice depends on the application's threading requirements.

============================================================
33. MEMORY RESOURCE VS SMART POINTER
====================================

Smart pointer:

std::unique_ptr<T>

answers:

"Who owns this object?"

Memory resource:

std::pmr::memory_resource

answers:

"Where/how should storage be obtained?"

They solve different problems.

Example:

A unique_ptr can own an object while that object's internal allocations may use a memory resource.

============================================================
34. SHARED_PTR THREAD SAFETY
============================

std::shared_ptr has important thread-safety guarantees around its ownership control mechanism.

Multiple shared_ptr objects that share ownership can generally be manipulated independently.

However, this does NOT mean the managed object itself is thread-safe.

Example:

std::shared_ptr<int> p;

Two threads accessing the same int without synchronization can still cause a data race if at least one access modifies the value.

For shared ownership with synchronization requirements, use appropriate synchronization such as:

* std::mutex
* std::lock_guard
* std::scoped_lock
* atomic operations
* std::atomic<std::shared_ptr<T>> where appropriate

C++20 provides atomic operations for shared_ptr specializations.

IMPORTANT:

"shared_ptr is thread-safe" does not mean:

"the object managed by shared_ptr is thread-safe."

============================================================
35. MEMORY LEAKS
================

A memory leak occurs when allocated storage remains unreachable or cannot be released correctly.

Example:

void leak() {
int* p = new int(100);

```
// Pointer is lost without delete.
```

}

RAII prevents many common ownership leaks:

void safe() {
auto p = std::make_unique<int>(100);
}

However, memory leaks can still occur with:

* shared_ptr cycles
* custom allocators
* global caches
* intentionally retained objects
* incorrect resource-management logic

============================================================
36. DANGLING POINTERS
=====================

A dangling pointer refers to an object whose lifetime has ended.

Example:

int* bad_pointer() {
int value = 42;
return &value;
}

The returned pointer refers to an object whose lifetime ended when the function returned.

Incorrect:

int* p = bad_pointer();

Dereferencing p is invalid.

Smart pointers can reduce many lifetime errors, but they cannot automatically correct every raw-pointer lifetime mistake.

============================================================
37. DOUBLE OWNERSHIP PROBLEM
============================

Incorrect:

int* raw = new int(42);

std::shared_ptr<int> p1(raw);
std::shared_ptr<int> p2(raw);

p1 and p2 have separate control blocks.

Both may eventually attempt to delete raw.

This creates undefined behavior.

Correct:

auto p1 = std::make_shared<int>(42);
auto p2 = p1;

Now both shared_ptr objects share the same control block.

40. COMMON MISTAKES
===================

Mistake 1:
Using new when make_unique is sufficient.

Prefer:

auto p = std::make_unique<T>();

---

Mistake 2:
Creating multiple shared_ptr from one raw pointer.

Avoid:

std::shared_ptr<T>(raw);

in multiple places.

---

Mistake 3:
Using shared_ptr when unique ownership is sufficient.

Prefer unique_ptr when there is one clear owner.

---

Mistake 4:
Using shared_ptr everywhere.

Shared ownership has additional bookkeeping and can obscure ownership design.

---

Mistake 5:
Creating shared_ptr(this).

Use enable_shared_from_this when the design requires shared ownership of an already shared object.

---

Mistake 6:
Using shared_ptr cycles.

Use weak_ptr for non-owning relationships.

---

Mistake 7:
Calling delete on placement-new objects.

Placement new does not imply that delete should be used.

---

Mistake 8:
Assuming smart pointers prevent all memory bugs.

They do not prevent:

* Buffer overflow
* Data races
* Invalid raw pointers
* Logic errors
* Incorrect lifetime assumptions
* Cyclic ownership

41. COMMON ERRORS
=================

ERROR:

std::unique_ptr<int> p1 =
std::make_unique<int>(10);

std::unique_ptr<int> p2 = p1;

Reason:

unique_ptr is non-copyable.

Correct:

std::unique_ptr<int> p2 =
std::move(p1);

---

ERROR:

std::shared_ptr<int> p(raw);
delete raw;

Reason:

The shared_ptr now owns raw. Manually deleting raw creates invalid ownership.

Correct:

std::shared_ptr<int> p(raw);

and allow the shared_ptr to manage the object.

---

ERROR:

std::shared_ptr<Node> a;
std::shared_ptr<Node> b;

a->next = b;
b->next = a;

Reason:

Possible ownership cycle.

Correct design:

Use weak_ptr for one non-owning direction.

43. PERFORMANCE CONSIDERATIONS
==============================

std::unique_ptr is designed to have minimal abstraction overhead, but its exact size and generated machine code depend on the pointer and deleter types and implementation.

For example:

std::unique_ptr<int>

will commonly have a size comparable to a raw pointer.

However:

std::unique_ptr<int, CustomDeleter>

may be larger depending on the deleter.

Therefore, do not claim that every unique_ptr is exactly 8 bytes.

shared_ptr generally has additional ownership bookkeeping and reference-counting overhead.

make_shared can reduce allocation overhead in common implementations by combining object and control-block storage.

Performance depends on:

* Compiler
* Optimization level
* Target architecture
* Allocator
* Object size
* Access pattern
* Threading
* Cache behavior

44. MEMORY CONSIDERATIONS
=========================

Important principles:

1. Object size is implementation-dependent.
2. Smart-pointer size is implementation-dependent.
3. Control-block layout is implementation-dependent.
4. Alignment affects object placement.
5. Allocation strategy affects performance.
6. Cache locality can affect performance.
7. Fragmentation can affect long-running programs.
8. Ownership models affect lifetime behavior.

Do not hard-code assumptions such as:

"shared_ptr is always 16 bytes."

or:

"control block is always 24 bytes."

Instead use:

sizeof(Type)

when implementation-specific measurements are required.

45. MEMORY FRAGMENTATION
========================

Frequent dynamic allocation and deallocation can contribute to fragmentation.

Potential solutions include:

* Object pools
* Pool allocators
* Monotonic memory resources
* Arena allocation
* Reusing containers
* Reserving container capacity
* Specialized allocators

Example:

std::vector<int> values;

values.reserve(1000);

reserve() can reduce repeated reallocations when the approximate required capacity is known.

============================================================
46. OBJECT POOLS
================

An object pool maintains reusable storage for objects of a particular type.

General flow:

Acquire object
|
v
Use object
|
v
Return object to pool
|
v
Reuse storage

Advantages:

* Reduced allocation frequency
* Predictable allocation behavior
* Potentially improved locality

Disadvantages:

* More complex lifetime management
* Pool lifetime must exceed allocated objects
* Thread synchronization may be required
* Memory may remain reserved

============================================================
47. MEMORY ARENAS
=================

An arena allocates storage from a larger region.

Typical strategy:

Arena
|
+--> Object 1
+--> Object 2
+--> Object 3
+--> Object 4

Instead of individually freeing each object, the entire arena can be reclaimed when the associated lifetime ends.

Arenas are useful when many objects share a common lifetime.

Examples:

* Compiler AST nodes
* Request processing
* Temporary parsing data
* Game-frame allocations
* Serialization buffers

48. SECURITY CONSIDERATIONS
===========================

Incorrect memory management can produce serious security vulnerabilities.

Common vulnerability classes include:

* Use-after-free
* Double-free
* Out-of-bounds access
* Buffer overflow
* Integer overflow leading to incorrect allocation
* Dangling pointers
* Uninitialized memory use

Smart pointers help with ownership management but do not replace secure programming practices.

Recommended practices:

* Prefer RAII.
* Prefer standard containers.
* Avoid unnecessary raw owning pointers.
* Validate allocation sizes.
* Avoid unchecked pointer arithmetic.
* Use sanitizers during development.
* Use static analysis.
* Keep dependencies updated.
* Minimize manual lifetime management.

============================================================
50. UNIQUE_PTR VS SHARED_PTR
============================

Use unique_ptr when:

* There is one clear owner.
* Ownership should be transferable.
* Shared ownership is unnecessary.

Use shared_ptr when:

* Multiple independent owners genuinely need to keep the object alive.
* Ownership is shared across components.
* Lifetime cannot naturally be represented by one owner.

Avoid shared_ptr simply because it is convenient.

A clear ownership model is generally easier to reason about and maintain.

============================================================
51. WEAK_PTR VS RAW POINTER
===========================

A raw pointer:

T*

does not normally express ownership.

A weak_ptr:

std::weak_ptr<T>

expresses:

"I may observe an object owned by shared_ptr, but I do not keep it alive."

weak_ptr can check lifetime safely:

if (auto p = weak.lock()) {
// object alive
}

A raw pointer does not provide this ownership/lifetime mechanism.

============================================================
52. RAII FOR NON-MEMORY RESOURCES
=================================

RAII is not limited to memory.

Example resources:

File:

class FileGuard;

Socket:

class SocketGuard;

Mutex:

std::lock_guard[std::mutex](std::mutex)

Database:

class DatabaseConnection;

The general design is:

constructor -> acquire resource

destructor -> release resource

This makes cleanup deterministic when the object lifetime ends.

============================================================
53. RULE OF ZERO AND MEMORY MANAGEMENT
======================================

Modern C++ often recommends the Rule of Zero.

If a class uses RAII members such as:

* std::string
* std::vector
* std::unique_ptr
* std::shared_ptr

then the class often does not need manually written:

* Destructor
* Copy constructor
* Copy assignment operator
* Move constructor
* Move assignment operator

Example:

class Manager {
private:
std::unique_ptr<int> data;
};

The compiler can automatically generate appropriate special member functions according to the type's semantics, subject to the usual rules.

This reduces manual resource-management code.

============================================================
54. EXCEPTION-SAFETY GUARANTEES
===============================

Modern C++ resource management should consider:

Basic guarantee:
The program remains in a valid state and resources are not leaked.

Strong guarantee:
An operation either succeeds or has no observable effect.

No-throw guarantee:
An operation does not throw exceptions.

RAII is a major technique for maintaining these guarantees.

Example:

auto resource =
std::make_unique<Resource>();

If later code throws, the resource is automatically released.

61. FAQ
=======

Q1. What is RAII?

A:
RAII connects resource lifetime to object lifetime so that destruction automatically releases the resource.

Q2. Why is unique_ptr preferred when there is one owner?

A:
It expresses exclusive ownership and supports automatic cleanup without shared reference counting.

Q3. Can unique_ptr be copied?

A:
No. It can be moved.

Q4. Can shared_ptr be copied?

A:
Yes. Copies share ownership.

Q5. Does weak_ptr own the object?

A:
No.

Q6. How do I access an object through weak_ptr?

A:
Use lock() to obtain a temporary shared_ptr if the object is still alive.

Q7. What causes a shared_ptr cycle?

A:
Two or more objects owning each other directly or indirectly through shared_ptr.

Q8. How is a shared_ptr cycle normally broken?

A:
Use weak_ptr for a non-owning relationship.

Q9. Does make_shared always use exactly one allocation?

A:
The standard specifies its semantics, while implementations commonly combine storage for the object and control block. Portable code should not depend on a specific allocation layout.

Q10. Is unique_ptr always exactly the same size as a raw pointer?

A:
No. The deleter type can affect its size.

Q11. Is shared_ptr thread-safe?

A:
Its ownership control mechanism supports required concurrent operations on separate shared_ptr objects sharing ownership, but the managed object itself is not automatically synchronized.

Q12. What is placement new?

A:
It constructs an object in storage supplied by the caller. It does not itself allocate that storage.

Q13. What is an allocator?

A:
An allocator provides an abstraction for obtaining and releasing storage for objects or container elements.

Q14. What is std::pmr?

A:
It provides polymorphic memory-resource facilities that allow allocation strategy to be selected at runtime through memory_resource interfaces.

Q15. Does smart-pointer usage guarantee memory safety?

A:
No. Smart pointers reduce many ownership errors but do not prevent all memory bugs.

67. SUMMARY
===========

Modern C++ memory management is primarily about expressing ownership and lifetime clearly.

RAII ties resource lifetime to object lifetime.

std::unique_ptr provides exclusive ownership.

std::shared_ptr provides shared ownership.

std::weak_ptr provides non-owning observation of shared objects.

std::enable_shared_from_this allows an already shared object to safely create additional shared_ptr instances referring to itself.

Custom deleters allow RAII to manage resources beyond ordinary memory.

Placement new constructs objects in existing storage without allocating that storage.

Alignment ensures that storage satisfies the requirements of the object type.

Allocators and std::pmr provide mechanisms for customizing storage strategies.

Memory pools and arenas can improve allocation behavior for specialized workloads.

Modern C++ does not eliminate all memory errors. Good ownership design, lifetime reasoning, synchronization, bounds checking, testing, and debugging tools remain essential.

============================================================
68. KEY TAKEAWAYS
=================

* Prefer automatic storage when dynamic allocation is unnecessary.
* Use RAII for deterministic resource management.
* Prefer std::unique_ptr for exclusive ownership.
* Use std::shared_ptr only for genuine shared ownership.
* Use std::weak_ptr for non-owning observation and cycle breaking.
* Use std::make_unique and std::make_shared for normal smart-pointer construction.
* Never create multiple independent shared_ptr objects from the same owning raw pointer.
* Do not create std::shared_ptr(this) when the object is already managed by shared ownership.
* Use std::enable_shared_from_this when appropriate.
* Custom deleters allow smart pointers to manage non-memory resources.
* Placement new constructs objects but does not allocate storage.
* Correct alignment is essential for manually managed storage.
* Allocators and PMR allow specialized allocation strategies.
* Smart pointers reduce ownership errors but do not guarantee complete memory safety.
* shared_ptr does not make the managed object thread-safe.
* Avoid assuming fixed sizes for smart pointers or control blocks.
* Use sanitizers and debugging tools to detect memory errors.
* Prefer clear ownership models over indiscriminate use of shared ownership.
* Use composition and RAII to reduce manual lifetime management.
* Measure performance instead of assuming that a particular memory-management technique is always faster.
